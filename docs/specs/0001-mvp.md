# Kanban MVP Scope

## Objective

Build a public Go CLI that turns any GitHub-backed repository into a simple local Kanban board by deriving the repository from the current working directory.

## Problem

The current shell approach is useful but too narrow:

- hard-coded to one repository
- terminal-only
- hard to reuse across repos
- not structured for future agent integrations

## Inputs Evaluated

### Existing shell seed: `gh-kanban.sh`

Strengths:

- proven workflow
- extremely cheap to run
- already uses `gh`, which is the right primitive for a user-level CLI

Weaknesses:

- hard-coded repo slug
- plain-text only
- not packaged, tested, or publishable

### External reference: `cline/kanban`

Assessment:

- excellent reference for agentic Kanban concepts
- strong precedent for local-server-plus-browser UX
- strong precedent for project autodetection and local state
- not the right codebase to fork for this product

Why it is not the base repo:

- it is a much larger product than needed for MVP
- it carries a runtime model centered on agent sessions, worktrees, and provider configuration
- it is tightly shaped around Cline-native flows and a JS/TS application stack
- forking it would make maintenance and public positioning heavier than necessary

## Decision

Use `cline/kanban` as a product and UX reference, not as the implementation base.

Build a fresh Go project that keeps these ideas:

- local web server
- zero-hosted dependency for core use
- repo autodetection from current working directory
- future room for agent-backed actions

Do not inherit these parts in MVP:

- task worktrees
- embedded agent runtime
- model/provider configuration
- complex local state stores

## MVP Features

- detect current git root from `pwd`
- resolve GitHub slug from `origin`
- fetch open milestones and open issues through `gh`
- render grouped terminal output
- render grouped web UI cards through a local Go server
- expose JSON output for scripting and future adapters
- ship as a single Linux-friendly binary

## Non-Goals

- replacing GitHub Projects
- running agents directly
- managing worktrees
- editing issues from the browser in v1
- persistent multi-repo state in v1

## Architecture

### Core model

- `repo`: detect git root and normalize GitHub remote
- `github`: call `gh` and normalize issue plus milestone payloads
- `app`: build a board view model and terminal rendering
- `web`: serve HTML and JSON from the same model

### Command surface

- `kanban print`
- `kanban json`
- `kanban serve`

Default command with no subcommand:

- `kanban` behaves like `kanban print`

### Web UI

- embedded server-side HTML template
- no Node dependency
- refresh button for manual reload
- milestone columns rendered as cards

## Agentic Future Scope

This repo should leave room for later adapters:

- `tsctl` delegate or spawn links from cards
- issue-to-agent launch actions
- structured prompts per label or milestone
- optional GitHub issue mutation flows

That is phase 2, not MVP.

## CI and Release

- validate on push and pull request
- build Ubuntu binaries on tags
- run `gofmt`, `go vet`, `go test`, `govulncheck`, and `gitleaks`

## Systemd

Provide a sample unit for always-on local or server deployment.

## Acceptance Criteria

- `kanban` prints a valid board for the current repo
- `kanban json` returns machine-readable board data
- `kanban serve` starts a local server and renders the same board
- `make check` passes locally
- GitHub Actions validate and release workflows are present
